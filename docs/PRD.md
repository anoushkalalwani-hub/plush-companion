## 1. Product Overview

### 1.1 Vision

Build an AI-powered stuffed animal that functions as an interactive, responsive conversational companion for elementary-school-aged children.

The device integrates a microphone, speaker, and Raspberry Pi 4 into a conventional stuffed animal. Children can speak naturally to the toy, ask questions, share stories, learn new concepts, and engage in creative conversations.

Unlike conventional voice assistants, this product prioritizes child safety, privacy, age-appropriate communication, and predictable behavior over unrestricted conversational capabilities.

The AI should feel engaging and personable without presenting itself as a human, replacing real relationships, or encouraging emotional dependency.

### 1.2 Core Product Principles

- **Safety over conversational ability:** When safety and conversational engagement conflict, safety takes priority.
- **Restricted generation:** The AI must operate within a predefined set of approved conversational capabilities.
- **Privacy by design:** Collect and retain as little personal information as possible.
- **Adult oversight:** Parents or guardians must have appropriate control over device configuration and privacy.
- **Predictable behavior:** The system must have deterministic fallback behavior when classification, generation, or validation fails.
- **Age-appropriate interaction:** All responses must be understandable and appropriate for elementary-school-aged children.
- **No autonomous agency:** The companion should not independently browse the internet, execute arbitrary tools, contact people, or perform external actions.

## 2. Target Audience

### 2.1 Primary Users

Children approximately 5–10 years old.

Expected interactions:

- Asking general knowledge questions.
- Discussing animals, science, nature, and everyday experiences.
- Requesting stories and imaginative adventures.
- Playing simple conversational games.
- Practicing vocabulary and basic educational concepts.
- Discussing ordinary emotions and social experiences.

### 2.2 Secondary Users

Parents and guardians.

Expected capabilities:

- Configure and activate the companion.
- Manage device connectivity.
- Configure age-appropriate interaction settings.
- Review privacy and data-retention settings.
- Delete stored information.
- Disable the microphone or conversation functionality.
- View device status and safety-related settings.

## 3. System Architecture

### 3.1 High-Level Architecture

The product consists of four primary components:

**A. Physical Device**
- Raspberry Pi 4 Model B.
- Microphone.
- Speaker.
- Physical power control.
- Physical microphone mute switch.
- Wi-Fi connectivity.

**B. Backend API**
- Device authentication.
- Session management.
- Conversation orchestration.
- Input classification.
- Output validation.
- Safety policy enforcement.
- LLM integration.

**C. AI Services**
- Speech-to-text.
- Hosted LLM.
- Moderation/classification services.
- Text-to-speech.

**D. Parent Interface**
- Device setup.
- Parent authentication.
- Privacy configuration.
- Device management.
- Data deletion.

### 3.2 Architectural Flow

Child speech → Raspberry Pi audio capture → Speech-to-text → Backend API → Input safety classification → Policy engine → LLM generation → Output safety validation → Text-to-speech → Raspberry Pi speaker.

**Important:** No generated response may be spoken until it has passed output validation.

If any required safety service is unavailable, the system must fail closed and use a predefined response.

## 4. Hardware Requirements

### 4.1 Raspberry Pi

Initial target: Raspberry Pi 4 Model B.

The Raspberry Pi is responsible for:

- Audio capture.
- Audio playback.
- Wake-word detection or push-to-talk input.
- Device connectivity.
- Backend communication.
- Basic device-state management.

The Raspberry Pi must NOT:

- Store API keys.
- Independently make unrestricted LLM requests.
- Store raw audio recordings persistently.
- Maintain unrestricted conversational memory.
- Execute arbitrary code generated by the LLM.

### 4.2 Audio

Requirements:

- Microphone input must support conversational speech.
- Speaker output must be intelligible at normal conversational volume.
- Audio capture must be activated through an explicit wake mechanism.
- The device must provide a visible or otherwise clear indication when its microphone is active.
- A physical microphone mute switch must disconnect or disable microphone capture.
- The device must provide an appropriate indication when disconnected from the backend.

Initial implementation should prioritize push-to-talk or an explicit wake-word interaction over continuous recording.

### 4.3 Physical Controls

Required:

- Power control.
- Microphone mute switch.
- Device status indicator.

Optional:

- Physical interaction button.
- Volume controls.
- Reset button.

## 6. AI Conversation Requirements

### 6.1 LLM Provider

The initial implementation should use a hosted LLM API.

OpenAI is the proposed first provider because it offers general-purpose language generation and a separate moderation API.

However, all provider-specific logic must be abstracted behind a common interface.

Example:

```
LLMProvider.generate(messages, constraints)
```

Required capabilities:

- System instruction support.
- Configurable response length.
- Configurable model.
- Timeout handling.
- Structured error handling.
- No unrestricted tool calling.
- No autonomous browsing.

Provider selection must not be treated as the primary safety mechanism.

### 6.2 Conversational Personality

The companion should:

- Be friendly and approachable.
- Use simple language.
- Respond naturally to children.
- Demonstrate curiosity.
- Encourage creativity and learning.
- Avoid unnecessarily lengthy responses.
- Ask occasional relevant follow-up questions.

Responses should generally be 1–4 short sentences.

The companion must not:

- Claim to be human.
- Claim to have a physical life or experiences it does not have.
- Encourage emotional dependency.
- Suggest that children should keep secrets from parents or trusted adults.
- Discourage relationships with family, teachers, or friends.
- Manipulate children into continuing conversations.

### 6.3 Approved Conversation Categories

The initial system should support:

| Category | Allowed behavior |
|---|---|
| General knowledge | Explain ordinary factual topics |
| Education | Age-appropriate explanations |
| Creative writing | Stories and imaginative scenarios |
| Animals and nature | Educational discussion |
| Games | Simple verbal games and riddles |
| Everyday conversation | Friendly, ordinary conversation |
| Emotional support | Basic empathy and encouragement |
| Social situations | General, nonjudgmental guidance |

The following categories require restricted handling:

- Medical questions.
- Personal information.
- Family conflict.
- Bullying and mistreatment.
- Abuse or unsafe situations.
- Dangerous activities.
- Sexual content.
- Self-harm-related disclosures.
- Requests for secrecy.
- Requests involving illegal activity.

These categories must have separately defined policies and tested response behavior.

## 7. Safety Architecture

This is the highest-priority subsystem.

### 7.1 Safety Philosophy

The LLM must never be trusted to enforce its own safety restrictions.

Safety must be implemented independently of the generative model through backend-enforced policy checks.

The system must operate using defense in depth.

### 7.2 Input Safety Classification

Every transcribed user input must pass through an input classification stage.

The classifier should identify:

- Ordinary conversational intent.
- Educational intent.
- Creative intent.
- Personal information disclosures.
- Sensitive disclosures.
- Dangerous requests.
- Medical questions.
- Potentially inappropriate content.
- Ambiguous or unclassifiable requests.

The classifier should return structured output:

```json
{
  "category": "educational",
  "risk_level": "low",
  "requires_special_handling": false,
  "confidence": 0.98
}
```

These values are illustrative. Confidence thresholds and category policies must be established through evaluation, not assumed from model-reported confidence.

Classification failures, timeouts, malformed output, and low-confidence cases must trigger predefined fallback behavior.

### 7.3 Policy Engine

Implement a deterministic policy engine.

The policy engine determines whether an interaction may proceed to generation, requires a predefined response, or must be blocked.

It must not rely exclusively on an LLM-generated classification.

Policy decisions must be logged using privacy-preserving event metadata.

### 7.4 Sensitive Disclosure Protocol

Sensitive disclosures require special treatment.

Examples:

- A child describing an unsafe situation.
- A child describing mistreatment.
- A child expressing serious emotional distress.
- A child disclosing personal identifying information.

Requirements:

- Respond calmly and supportively.
- Never blame or shame the child.
- Never interrogate the child or attempt to investigate.
- Never promise secrecy.
- Encourage speaking with a trusted adult.
- Use expert-reviewed response templates.
- Do not independently contact third parties.
- Do not retain sensitive disclosures as conversational memory.

A qualified child-safety professional must review this protocol before deployment.

### 7.5 Output Validation

Every LLM-generated response must pass through an independent validation stage.

Validation must check:

- Age appropriateness.
- Restricted content.
- Personal information exposure.
- Dangerous instructions.
- Inappropriate emotional framing.
- Unsupported medical or other high-stakes advice.
- Compliance with the applicable conversational category.

If validation fails, the generated response must be discarded.

The system must never attempt to repair an unsafe response by simply asking the same LLM to rewrite it without an independent subsequent validation.

### 7.6 Fail-Closed Behavior

The system must use predefined fallback responses when:

- Input classification fails.
- Output moderation fails.
- The LLM times out.
- The backend loses connectivity.
- The response is malformed.
- The response fails validation.
- A safety decision cannot be made reliably.

Example fallback:

> "I'm not sure how to help with that. Maybe we can talk to a grown-up you trust."

Fallback responses must be reviewed for their specific context. Sensitive disclosures should have dedicated responses rather than a generic refusal.

## 8. Memory and Personalization

### 8.1 Initial MVP

The initial MVP should operate without persistent child conversation memory.

Session context may be maintained temporarily to support conversational continuity.

The system must not persist:

- Raw audio.
- Full transcripts by default.
- Sensitive disclosures.
- Personal identifying information.
- Inferred psychological profiles.
- Private family information.

### 8.2 Future Personalization

Future versions may support limited, parent-configurable preferences.

Examples:

- Preferred companion name.
- Favorite animals.
- Preferred story themes.
- Preferred language.

Only non-sensitive preferences should be considered for persistent storage, with appropriate parental authorization and deletion controls.

## 9. Privacy and Security

Privacy must be incorporated into the initial architecture rather than added after development.

Requirements:

- All device-to-backend communication must use encrypted transport.
- API credentials must remain server-side.
- Every device must have independently revocable credentials.
- Raw audio must not be stored persistently by default.
- Data collection must be minimized.
- Retention periods must be explicitly defined.
- Parents must have appropriate data-deletion controls.
- Device authentication must prevent unauthorized access.
- Database access must follow least-privilege principles.
- Error logs must not contain unnecessary personal information.
- The microphone must have a physical mute mechanism.
- Security-sensitive configuration must not be modifiable by the child.
- The product must undergo privacy and child-safety review before deployment with real children.

## 10. Parent-Facing Application

The parent application is not required for the first conversational prototype, but its interfaces should be anticipated in the backend architecture.

Future functionality:

- Parent account creation.
- Device pairing.
- Wi-Fi configuration.
- Device activation and deactivation.
- Microphone status.
- Volume settings.
- Privacy settings.
- Data deletion.
- Retention configuration.
- Safety policy version visibility.
- Software updates.

The parent application must not expose sensitive child conversations as a default feature.

## 11. API Requirements

Proposed initial endpoints:

| Endpoint | Purpose |
|---|---|
| `POST /api/v1/devices/register` | Register device |
| `POST /api/v1/devices/authenticate` | Authenticate device |
| `GET /api/v1/devices/status` | Retrieve device status |
| `POST /api/v1/sessions` | Create session |
| `POST /api/v1/sessions/{id}/message` | Process conversation |
| `DELETE /api/v1/sessions/{id}` | End session |
| `GET /api/v1/parent/settings` | Retrieve parent settings |
| `PATCH /api/v1/parent/settings` | Update parent settings |
| `DELETE /api/v1/parent/data` | Request eligible data deletion |

All endpoints must implement authentication, authorization, input validation, and appropriate rate limiting.

The conversation endpoint must not expose an unrestricted direct-to-LLM interface.

## 12. Functional Requirements and Acceptance Criteria

### 12.1 Basic Conversation

- Child can initiate a conversation.
- Audio is transcribed.
- The backend processes the message.
- The LLM generates a response when permitted.
- The response is validated.
- Approved text is converted to speech.
- The Raspberry Pi plays the audio.

**Acceptance:** A normal educational conversation completes successfully without requiring manual intervention.

### 12.2 Safety

- Every interaction is classified.
- Every generated response is validated.
- Restricted categories use the correct policy.
- Validation failures never reach the speaker.
- Service failures produce safe fallback behavior.

**Acceptance:** The system passes a documented adversarial test suite with no known critical safety failures. This is a release gate, not proof of complete safety.

### 12.3 Privacy

- No persistent raw audio by default.
- No persistent sensitive conversation memory.
- Device credentials are protected.
- Parent-authorized deletion works as specified.

**Acceptance:** Privacy tests verify that data is not retained beyond configured policies.

### 12.4 Reliability

- Backend timeouts are handled.
- Network disconnections are handled.
- Device reconnects gracefully.
- No unvalidated response is played.
- Device state remains consistent after restart.

**Acceptance:** Simulated service failures never cause unrestricted or unvalidated responses.

## 13. Nonfunctional Requirements

| Requirement | Target |
|---|---|
| Response length | 1–4 short sentences |
| Conversation style | Elementary-school appropriate |
| Backend availability | Target 99% during initial pilot |
| Authentication | Required for every device |
| Transport security | HTTPS |
| Memory | Disabled by default |
| Tool access | Disabled by default |
| Audio storage | Disabled by default |
| Response generation | Configurable timeout |
| Error handling | Safe fallback |

Latency should be measured during prototyping. Establish an acceptable end-to-end conversational response target after testing the selected speech and LLM providers.

## 14. Development Roadmap

> The working build order differs from this roadmap (safety gates exist from the first milestone). See [DEVELOPMENT.md](DEVELOPMENT.md) and decision D-001 in [DECISIONS.md](DECISIONS.md).

### Phase 1: Hardware Prototype

Goal: Establish basic audio functionality.

Tasks: Configure Raspberry Pi OS. Connect microphone. Connect speaker. Implement audio capture. Implement audio playback. Establish backend connectivity.

Deliverable: Working Raspberry Pi audio interface.

### Phase 2: Backend and LLM Integration

Goal: Establish a working conversational pipeline.

Tasks: Initialize FastAPI. Implement device authentication. Create conversation endpoint. Integrate speech-to-text. Integrate hosted LLM. Integrate text-to-speech. Implement session management.

Deliverable: End-to-end conversational prototype.

### Phase 3: Safety Infrastructure

Goal: Implement independent safety enforcement.

Tasks: Implement input classification. Implement deterministic policy engine. Implement restricted response templates. Implement output validation. Implement failure handling. Implement safety event logging. Build adversarial evaluation dataset.

Deliverable: Safety-gated conversational prototype.

### Phase 4: Product Experience

Goal: Make the device usable as a stuffed animal companion.

Tasks: Implement wake-word or push-to-talk. Implement conversational personality. Tune audio playback. Implement status indicators. Improve response latency. Implement device reconnection.

Deliverable: Integrated stuffed animal prototype.

### Phase 5: Parent Controls and Pilot Preparation

Goal: Prepare the system for controlled testing.

Tasks: Build parent authentication. Implement device pairing. Implement privacy controls. Implement data deletion. Complete security review. Complete child-safety review. Conduct supervised usability testing.

Deliverable: Reviewed pilot candidate.

## 15. Agent Development Instructions

AI coding agents working on this project must follow these rules.

### 15.1 General Instructions

- Treat this PRD as the source of truth.
- Do not independently expand product scope.
- Do not introduce autonomous agent functionality.
- Do not bypass the backend safety architecture.
- Do not implement unrestricted LLM access.
- Do not store sensitive information for convenience.
- Do not hardcode provider-specific logic throughout the codebase.
- Write modular, testable code.
- Document architectural decisions.
- Include tests with every implemented feature.

### 15.2 Safety-Specific Instructions

- Never assume system prompts guarantee safe behavior.
- Never allow generated content to bypass output validation.
- Never stream unvalidated generated text to speech.
- Never treat vector retrieval as a safety boundary.
- Never permit arbitrary tool execution.
- Never silently fail open when moderation services are unavailable.
- Never add persistent child memory without explicit product approval and privacy review.
- Never invent safety policies when an existing policy is unclear.
- When requirements conflict or are ambiguous, document the conflict and request human approval.

### 15.3 Development Workflow

Before implementing a feature:

1. Read the relevant PRD sections.
2. Identify dependencies.
3. Propose the implementation.
4. Identify safety and privacy implications.
5. Define acceptance tests.
6. Implement the feature.
7. Run tests.
8. Document completion and outstanding limitations.

Agents must not independently approve safety-critical changes.

## 17. Initial Definition of Done

The MVP is considered technically complete when:

- The Raspberry Pi can capture and play audio.
- The backend can process authenticated device requests.
- Speech-to-text and text-to-speech work.
- The hosted LLM generates age-appropriate conversational responses.
- Input classification is implemented.
- Deterministic safety policies are enforced.
- Every generated response passes independent validation.
- Sensitive disclosures trigger predefined response protocols.
- Failure states cannot bypass safety validation.
- Persistent conversation memory is disabled by default.
- Basic privacy and security tests pass.
- Documentation and automated tests are complete.

Technical completion does not constitute approval for unsupervised use by children. A separate child-safety, privacy, and security review is required before deployment.
